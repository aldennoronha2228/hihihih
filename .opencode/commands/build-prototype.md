Build a real prototype workflow for this idea: **$ARGUMENTS**

Follow the repository's `AGENTS.md` and `docs/OPENCODE-WIREUP-BLENDER.md`. The user wants a working physical design, not a scaffold. Blender remains an external MCP tool; WireUp remains the electronics project and frontend.

## Run this workflow

1. **Understand the idea.** Extract function, size/use, motion, inputs, power, constraints, and the simulation outcome the user wants. Keep the idea's domain; an RC car is a supported path, not a reason to redirect to a drone or reject the task. If an assumption is low risk, state it and proceed.
2. **Check tools and project context.** Inspect available WireUp and Blender MCP tools and their descriptions. Check WireUp health and identify the intended project. Never mutate an unrelated project. If one MCP is unavailable, tell the user which phase is affected and continue independent phases.
3. **Read WireUp catalog feasibility.** Search for candidate real parts and capture exact catalog type, manufacturer, SKU, pinout, voltage/current limits, dimensions, and sources where available. Treat this as an early shortlist so mechanical design can fit plausible parts; do not require every subsystem to already be catalog-supported.
4. **Model the mechanical product in Blender.** Use the Blender MCP to create the custom geometry from the idea and its requirements. For an RC car, model the actual chassis, wheels/tires, axles or drivetrain, steering geometry, body, and mounting features. Source standard-part geometry from manufacturer CAD; when unavailable, reconstruct it from official dimensioned drawings. Record sources and units. Do not render envelope guides, boxes, or proxy meshes as actual components. Start with the custom mechanical product even if some electronics are not yet selected.
5. **Build the actual electronics in WireUp.** Choose compatible parts that exist in the catalog, then create/update the intended circuit and firmware through WireUp MCP using current project state/revision. For an RC car, cover controller/receiver, ESC, drive motor, steering servo, battery, and requested sensors. If something is unsupported, finish supported choices and wiring, and leave a clearly named external integration point. Never invent a WireUp catalog item or pin.
6. **Fit exact electronics models in Blender.** For each selected WireUp part, import manufacturer CAD when available; otherwise reconstruct from its official mechanical drawing/datasheet. Fit the exact part-number model to the assembly and update the Blender exports. If exact geometry is unavailable, mark only that model unresolved and keep progressing on the rest.
7. **Prepare simulation readiness.** Link each WireUp instance/type to its Blender variant. Separate render meshes from collision geometry. Record evidence-backed dimensions, mass, center of mass, inertia, joints, tire/contact parameters, and actuator properties in a source-traceable physics profile. Connect real firmware outputs and simulated timestamps to supported ESC/motor/servo models. Do not claim a subsystem is simulated unless its mechanics/control loop is actually connected. If RC vehicle dynamics are not implemented, report that precise gap while still delivering the design/model/electronics outputs.
8. **Publish real artifacts.** Export actual browser-ready GLBs from Blender to `public/models/3d/`, write/update `manifest.json` with exact WireUp component types and per-model manufacturer/SKU/source metadata, and store physics profiles separately. Keep only successful exports in the manifest. The WireUp 3D tab displays these assets and allows per-instance variant selection; it must never create missing models itself.
9. **Report plainly.** Summarize the idea brief, actual WireUp selections/wiring/firmware, Blender files and their geometry sources, which assets appear in the viewer, simulation behaviors truly running, and unresolved items. Distinguish created from verified. Do not run builds or broad tests unless the user asks; do inspect the outputs and project state needed for an honest report.

Missing catalog coverage, one missing manufacturer model, or one unsourced physical value is not a stop condition for the entire RC-car path. Continue the supported work, label the gap precisely, and leave the project in a state that can be extended when that item becomes available.
